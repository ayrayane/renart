# Security

## Reporting a vulnerability

Do not open a public issue. Report privately through GitHub's "Report a vulnerability" (Security tab of this repository). Expect an answer within 5 working days, and a fix or a mitigation plan within 30 days for high and critical issues. Only the latest release is supported.

## Threat model

Renart lets a GitLab user with the **Developer** role launch an AI agent that reads a merge request, an issue or a pipeline and writes back to GitLab through a dedicated **bot account**.

- **Everything the agent reads is untrusted**: MR and issue text, comments, diffs, CI logs. Someone can write instructions there (prompt injection). The system prompt is not a security boundary; the limits below are.
- **A run only touches its own object.** Every GitLab tool is bound to the run's project and to its own MR, issue or pipeline (plus that pipeline's MR and jobs, or that MR's pipelines). Text cannot point the bot at another MR, a confidential issue or other jobs.
- **What the bot writes is filtered**: GitLab quick actions are neutralised, outside images are dropped (they would leak data or the reader's address), `@all`/`@here` cannot ping, and closing keywords only work for the run's own issue. Group mentions are not filtered: restrict them in your GitLab settings.
- **Code changes are proposals.** The agent never pushes to an existing branch: it opens a **draft** MR from a `renart/run-*` branch, pushed with `ci.skip`. A person reviews it and starts its pipeline. Merge request pipelines created when the MR opens still run as the bot if your CI defines them: see the settings below.
- **No shell.** The agent edits files through guarded tools limited to the clone (no `.git`, no symlinks, no path outside the repository).
- **Workflows.** Instance workflows come from the workflows project. A repository can add its own in `.renart/workflows/` but cannot replace an instance workflow. Anyone who can push to a repository's default branch controls that repository's own workflows: protect that branch.

## Secrets

| Secret | Where | Rotate |
|---|---|---|
| Bot token (`secrets.bot`) | orchestrator, runner and graph build pods | GitLab, then `kubectl -n <ns> edit secret`, restart the orchestrator |
| Anthropic key or token (`secrets.anthropic`) | runner pods only | replace the Secret |
| Orchestrator token (`secrets.orchestrator`, read-only) | orchestrator | replace the Secret |
| `renart-internal` (HMAC key for internal tokens) | orchestrator, generated by the chart | delete the Secret and upgrade the release |

The user's own GitLab token (OAuth, `read_api`) never leaves the orchestrator. The audit log (`/data/audit.jsonl`) records who ran what, with the free-text instructions users typed: treat it as personal data.

## Deployment requirements

- TLS on the ingress, and a CNI that enforces NetworkPolicies (the chart's policies keep runner pods off private addresses and the Kubernetes API).
- `/internal` routes are served on a separate port (8081) that the Ingress never routes to.
- **Bot account**: lowest role that works (Developer), a group or project access token with an expiry rather than a personal token, protected branches, and CI/CD variables marked **protected** (they are then not exposed to `renart/run-*` branches). Limit the job token's reach with the job token allowlist.
- Pin images by digest in production (`images.*`, `agentgateway.image`).
- One user can run at most `orchestrator.maxRunsPerUser` runs at once (default 3).

## Out of scope

Merge requests from forks (refused), the quality of the model's output, and a compromised model provider or GitLab instance.
